Goal-conditioned PPO teacher for the variable-goal Push-T experiment (`CODEX_CONTEXT.md` on main, commit 9915e87),
plus the shared variable-goal environment `PushTVarGoal-v1`. This file is the running log for this part of the

In the variable-goal design, PPO is trained first: random block, stick-tip and goal positions across Q1–Q4, with the
goal coordinates in the observation. Nathan's goal-conditioned BC is then distilled from it ("PPO and distilled BC").
The transformer later sees the same states with the goal fields removed.

## How to run

- **Notebook (Kaggle):** [`notebooks/Train_PushT_State_PPO_VarGoal.ipynb`](../notebooks/Train_PushT_State_PPO_VarGoal.ipynb).
  Kaggle → New notebook → File → Import → upload it. Settings: **GPU T4**, **Internet on**.
  Use **Save Version → Save & Run All** for the long run; outputs in `/kaggle/working/state_rl/<session>/` are kept with the version.
- **Code:**
  - [`pusht_vargoal.py`](pusht_vargoal.py): the environment. Import it, then `gym.make("PushTVarGoal-v1", ...)`.
    **Everyone using variable goals should use this file**, so success is measured the same way.
  - [`pusht_state_ppo.py`](pusht_state_ppo.py): `preflight` (GPU env checks + `observation_contract.json`) and `eval`
    (per-quadrant evaluation, checkpoint selection, freeze check).
  - [`run_ppo.py`](run_ppo.py): runs ManiSkill's unchanged `ppo.py` with the new env registered.
  - [`make_tip_starts.py`](make_tip_starts.py): builds `assets/tip_start_qpos.npz` (already built; rerun only if `TIP_BOX` changes).
- **Notebook source:** generated by `python state_rl/build_notebook.py`, which embeds the files above. Never edit the notebook's code cells by hand.
- **Tests (CPU simulator, about 5 s):** `python -m unittest state_rl/tests/test_vargoal_cpu.py -v`.
  On a headless machine without a GPU, install mesa's software Vulkan driver (`mesa-vulkan-drivers`) and set
  `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json`.

## The variable-goal environment

PushT-v1 hard-codes the goal. `PushTVarGoal-v1` changes only the reset and the success transform:

- **Goal:** sampled per episode in quadrants around the origin (−0.156, 0.0), i.e. PushT-v1's goal x, centred in y.
  Goals lie within ±0.10 m in x and ±0.20 m in y of the origin, excluding a 0.02 m (x) / 0.03 m (y) band around
  the axes so neighbouring quadrants do not share near-identical goals. Orientation stays fixed at 5π/3.
  `goal_quadrants=(1, 2, 3)` restricts sampling; `reset(options=dict(goal_xy=...))` fixes goals.
- **Quadrants:** dx = x − (−0.156), positive = away from the robot base.
  Q1: dx > 0, y > 0 · Q2: dx < 0, y > 0 · Q3: dx < 0, y < 0 · **Q4: dx > 0, y < 0** (the held-out quadrant).
- **Success check:** PushT-v1 computes one goal transform at load time. Here there is one per environment,
  recomputed at every reset; without this a moved goal is scored against the old one.
- **T block start:** uniform in x ∈ [−0.30, −0.02], y ∈ [−0.28, 0.28], random rotation, **independent of the goal's
  quadrant**, with distance to the goal in [0.08, 0.30] m (mean 0.18 m over 300 resets). The cap keeps pushes
  similar in length to PushT-v1's, so 100 steps should suffice.
- **Stick-tip start:** random point in x ∈ [−0.36, 0.00], y ∈ [−0.30, 0.30], at least 0.15 m from the T. Drawn from a
  library of 600 arm poses that reach those points (built by driving the tip there with the end-effector controller),
  plus PushT-v1's usual 0.02 rad joint noise. This avoids inverse kinematics on the GPU.
- **Unchanged:** observation, action space, controller, episode length, dense reward (it already reads the goal's
  live position; its rotation term uses the fixed goal angle), success threshold.

**Measured stick-tip reach** at table height (CPU sim, end-effector controller, 1 cm tolerance):
x ∈ [−0.40, 0.05], y ∈ [−0.45, 0.45] (base at x = −0.615). All regions above keep about 0.1 m margin inside it.
See `workspace_layout.png` for 300 sampled resets.

**Checks done (CPU, 2026-11-23):** goals land in the requested quadrants with the gap; quadrant mix is balanced; the
observation carries the new goal at 21:23; T and tip constraints hold over 60 resets; a T placed exactly on a moved goal
succeeds and the old fixed goal no longer counts; at PushT-v1's own goal the transform and goal pose are identical to the
original. A perfectly placed T scores 0.948 overlap in both envs (the overlap is computed on a pixel grid).
**GPU preflight (Kaggle T4, 2026-11-23):** all 10 checks pass, including partial resets (PPO's auto-reset) and per-env success.

## Run 1: pilot, 25M steps (2026-11-23)

ManiSkill's PushT state PPO recipe, unchanged except the env id and evaluation settings: 1024 envs, 100-step rollouts,
8 epochs, 32 minibatches, gamma 0.99, lr 3e-4 constant, seed 1. About 12.5k steps/s on one T4 (42 min).

Success-once (64 mixed eval envs) stayed near 0 until about 12M steps, then rose: 30% at 17M, 44% at 22M, 50% at 25M.
Selected `final_ckpt.pt`; test success-once Q1 56%, Q2 63%, Q3 57%, Q4 64% (at end 44/52/55/64%). **Fails the bar**,
curve still rising, quadrants even, so more budget rather than an env change.

## Run 2: continuation from the pilot (2026-11-23, stopped)

Loaded the pilot's `final_ckpt.pt` via `--checkpoint` (weights only) for 25M more steps. Iteration 1 (before any
update): 67% success-once. Iteration 11 (1M steps): 0%, and still under 5% at 8M steps. Likely cause: ppo.py does not
save the optimizer, so Adam restarted; its first updates take about full-learning-rate steps in every weight, which wrecked
the trained policy. Not proven, but the "fine, then collapses at once" pattern fits. **Fix:** `run_ppo.py` now saves Adam's
state next to each checkpoint (`<ckpt>.pt.optim`) and restores it on `--checkpoint`. Decided to rerun from scratch instead.

## Run 3: fresh, 50M steps (2026-11-23) → frozen

Same recipe as Run 1, 50M steps (~70 min training on a T4), seed 1. Last 10 checkpoints on validation: worst-quadrant
success-once 75–91%. Selected `final_ckpt.pt` (91% worst, 93% mean). Test: see the table above. **Passes the bar.**
Note: some earlier checkpoints reached the goal and then pushed the T off it again (e.g. `ckpt_411`: Q3 85% once, 25% at
end); the selected one mostly holds the goal.
